# Правила работы в этом проекте

Для любого агента. Владелец повторял это не раз — читай до того, как писать код.

## Как мы работаем

- **Частями.** Задача делится на небольшие куски. Кусок → показать владельцу → ревью → коммит → следующий. Не пиши весь этап целиком.
- **Ничего не коммитить без разрешения.** Ждём слова «ок» или «коммить». Ветка — своя (`feat/...`), не `main`.
- **Скорость важна.** Не пересказывай план словами, если можно сразу показать код. Не объясняй по три абзаца то, что видно в диффе.
- **Прежде чем спорить — проверь.** Утверждения о коде подтверждай чтением файла, а не памятью.
- **Говори цену.** Если вариант избыточен для сегодняшнего размера проекта — скажи это прямо и предложи дешёвый.

## Комментарии и docstring

- **Одна короткая фраза.** Не поэма. Ни разбора альтернатив, ни пересказа спеки, ни истории решения.
- **Второй абзац — только если без него поведение непонятно.** Такое бывает редко.
- **Развёрнутое «почему» идёт в сообщение коммита,** не в тело функции.
- Плохо: восемь строк про то, почему выбраны две ссылки вместо `GenericForeignKey`.
  Хорошо: `# Две ссылки вместо одной общей: так база сама подчистит удалённые карточки.`

## Слои бэкенда

| Где | Что там лежит |
|---|---|
| `models.py` | поля, ограничения, `Meta`. Никаких вычислений «для API» |
| `queryset.py` | выборки и знание о том, как поля устроены |
| `services.py` | функции, которые читают или пишут базу |
| `utils.py`, `utils/` | чистые функции: базы не касаются |
| `rules.py` | правила предметной области (чистые) |
| `constants.py` | числа, пределы, перечисления, имена заголовков |
| `admin.py` | только админка |

Правило разделения простое: **пишет или читает базу → `services`; не касается базы → `utils`.**

Чистый помощник не заводится в корне приложения — он лежит в `utils/` этого приложения. Однородная структура приложения: `models/`, `admin/`, `utils/`, `services.py`, `constants.py`, при надобности `queryset.py` и `rules.py`.

## Импорты

Импортируй саму функцию, а не модуль:

```python
# так
from apps.common.services import visitor
source, learner = visitor(init_data=...)

# не так
from apps.common.services import learners
source, learner = learners.visitor(init_data=...)
```

Пакет отдаёт своё содержимое сам: в `__init__.py` перечислены функции и классы вместе с
`__all__`, поэтому имя файла в импорте не участвует. Завёл новый файл в пакете — допиши
его в `__init__.py`.

## Файлы и структура

- **Виды и сериализаторы — по файлу на ручку,** пакетом (`views/cards.py`, `serializers/state.py`).
- Один файл — одна ответственность. Не сваливать всё в общий `views.py`.
- Направление зависимостей: `common` — общее для всего и ни от кого не зависит. `learning` и `vocabulary` зависят от `common`. `api` зависит от всех. Наоборот — никогда.
- `common` не знает про HTTP: `Request`, заголовки и права остаются в `api`, а в `common` уезжают аргументы (`is_bot=True`, а не `request`).

## Модели

- Необязательное поле — `**BLANK_AND_NULL` из `common/constants.py`.
- `created_at` и сортировка «свежие сверху» — из `BaseModel`, своё не объявлять.
- Django 6: `models.CheckConstraint(condition=...)`, не `check=`.
- `Meta` наследуется как `class Meta(BaseModel.Meta)`. От `Meta` абстрактной модели с `abstract = True` не наследоваться — потеряется таблица.

## Настройки

- Всё, что подкручивается по опыту, — переменная окружения, не константа в коде.
- Объявления живут **в конце `settings.py`**, в огороженных блоках с заголовком и строкой конца.
- У каждой переменной — строка, зачем она.
- Ту же переменную добавить в `.env.example` с пояснением.

## Тесты

- `pytest` + `pytest-django`, запуск `make test`. База должна быть поднята: `docker compose up -d db`.
- Фронтенд — `vitest`, только на чистые функции (сборка сеанса, разбор жеста). Экраны проверяются глазами.
- **Тест не читает те же настройки, от которых зависят его ожидания.** Задавай их в тесте через `override_settings`, иначе тест подтвердит любую конфигурацию, включая сломанную.
- Отдельный тест доказывает, что код читает настройки, а не константы в себе: подсунь ему другую лестницу.
- Docstring теста — одна фраза, зачем он.

## Фронтенд

- Оформление приложения владельцу нравится. **Новую логику накладывать на текущий вид**, ничего не переставляя: только добавлять элементы.
- Дизайн менять — только по прямой просьбе. Про внешний вид спрашивать отрисованными макетами, а не описаниями.
- Остальное — в глобальных правилах: CSS Modules, `rem` кратно 0.2, переменные в `_variables.scss`, порядок `#region` в SFC.

## Коммиты

- **Коммитить перечисленными путями** (`git commit -o путь ...`), а не `git add -A`: иначе в историю уезжают скриншоты, слепки страниц и прочий мусор проверки.
- Сообщение по-русски: заголовок в одну строку, тело — «почему», а не «что» (что видно в диффе).
- В конце: `Co-Authored-By: Claude Opus 5 (1M context) <noreply@anthropic.com>`.
- Спеки — `docs/superpowers/specs/`, планы — `docs/superpowers/plans/`.
