# Mufradat Bot — дизайн

Дата: 2026-08-05. **Ревизия 5** — переписана целиком под фактическое состояние кода.

Что изменилось против ревизии 4: убраны нормализация арабского, поиск похожих
записей, поля `source` и `topic`; сущность администратора свелась к одной переменной
окружения; появились бот с вводом слов и структура `backend/`.

---

## 1. Что строим

Закрытое приложение в Telegram для группы ~10 человек, которые вместе учат
литературный арабский по учебнику «العربية بين يديك». Колода общая на всех, прогресс
у каждого свой.

| Вход | Кому | Зачем |
|---|---|---|
| Telegram Mini App | всем | учёба по карточкам |
| Чат с ботом | админу | ввод слов с телефона |
| Админка Django | staff | ввод и правка с компьютера, загрузка картинок |

Бот: **@mufradat_cards_bot**, имя «مفردات».

## 2. Роли

Админ ровно один — владелец. Его Telegram ID лежит в `ADMIN_TELEGRAM_ID`; отдельной
модели нет, потому что список из одного элемента не нуждается в таблице. Проверка в
одном месте — `apps/bot/permissions.is_admin`.

Staff в админке — обычные пользователи Django с паролем. Это отдельный механизм: у
ученика нет пароля, у staff нет Telegram ID.

## 6. Модель данных

### Entry — единица заучивания (есть в коде)

| Поле | Тип | Примечание |
|---|---|---|
| `kind` | choices | `word` \| `phrase` |
| `arabic` | text | с огласовками, как ввёл владелец |
| `translation_ru` | text | |
| `transliteration` | text, blank | различает пары вроде `katabta` / `katabti` |
| `image` | ImageField, null | загружается через админку |
| `created_at` | timestamptz | «последние N добавленных» в тренировке |

Ограничение: `unique(arabic, translation_ru)`. По **точному** арабскому — пара «к
мужчине / к женщине» различается только последней харакой, и сравнение по скелету
запрещало бы женскую форму.

Фразы — полноценные единицы, а не примеры: «مَا اسْمُكَ؟» учится как карточка. Тип
определяется при вводе: многословное арабское → фраза, однословное → слово.

### Появится на этапе 5

- `TelegramUser` — ученик: `telegram_id` (PK), `username`, `first_name`,
  `new_per_day` (лимит новых карточек в день), `created_at`.
- `UserProgress` — одна строка на (ученик, единица, направление): `due` (timestamptz,
  индекс), `fsrs_state` (JSONField), `updated_at`;
  `unique(telegram_user, entry, direction)`.
- `ReviewLog` — см. §12, вопрос открыт.

### Появится на этапе 7

- `Sentence`, `SentenceEntry` — примеры употребления, их создаёт генерация.

### Отложено без даты

Словоформы (`kind=form`, `base`, `person`, `tense`, `pos`) — карточки вида «его
машина», «я пишу». Владелец хотел их видеть; решение отложено до рабочего цикла
повторений. Пройденные местоимения: `ana`, `huwa`, `hiya`, `anta`, `anti`, `nahnu`.

## 7. FSRS — проверенные факты

Библиотека осмотрена, чтобы не проектировать вслепую:

```
Card().to_dict() → {card_id, state, step, stability, difficulty, due, last_review}
Rating           → Again=1, Hard=2, Good=3, Easy=4
Scheduler().review_card(card, rating, review_datetime=None) → (Card, ReviewLog)
```

Отсюда хранение: словарь целиком в `fsrs_state`, а `due` дублируется отдельной
индексированной колонкой — внутри словаря это строка, а по нему идёт главный запрос
«что пора сегодня».

**FSRS считается на сервере.** Причины: «Тренировка» обязана не менять состояние, и
на сервере это просто отсутствие вызова — ломать нечего; библиотека на Python, иначе
нужен порт на JS и синхронизация двух реализаций; прогресс переживает переустановку
Telegram. Плата — запрос на карточку, лечится оптимистичным интерфейсом.

## 8. Наполнение базы

### Ввод через бота (работает)

Строка `арабское | перевод` или `арабское | перевод | транслитерация`.

**Порядок частей не важен.** Каждая часть определяется по алфавиту: арабский,
кириллица и латиница лежат в непересекающихся диапазонах Unicode. Поэтому
`بَيْت | дом`, `дом | بَيْت` и `bayt | дом | بَيْت` разбираются одинаково.

Дубли не падают ошибкой — бот отвечает «Уже есть». Нераспознанная строка возвращает
причину и формат. Не-админ получает отказ с кнопкой приложения.

### Ввод через админку (работает)

То же самое с компьютера, плюс загрузка картинок и правка типа, если эвристика
«слово или фраза» ошиблась.

### ИИ-генерация (этап 7)

Единственное, что делает ИИ, и только по команде админа: предложения-примеры из
пройденной лексики и одно-два новых слова в неделю. Правила — в редактируемом
`backend/content/curriculum.yaml`: темы, примеры, список пройденных местоимений,
максимум одно новое слово на предложение. Главный рычаг — примеры: модель ловит стиль
по образцам точнее, чем по описанию.

Распознавания страниц учебника **нет**: владелец вводит слова сам, и это снимает
главный риск проекта — потерянные при распознавании огласовки.

## 9. Учёба в Mini App

Каждая единица даёт две независимые карточки: `ar_ru` и `ru_ar`.

| Направление | Лицо | Оборот |
|---|---|---|
| `ar_ru` | арабское | перевод, транслитерация, **картинка** |
| `ru_ar` | перевод + **картинка** | арабское, транслитерация |

Картинка на лице `ar_ru` выдала бы ответ — вместо припоминания перевода получилось бы
узнавание картинки. На `ru_ar` она арабского не выдаёт, а припоминание от образа
сильнее, чем от русского слова.

| Режим | Что даёт | Пишет в FSRS |
|---|---|---|
| На сегодня | что пора по расписанию | да |
| Новые | единицы без прогресса, с суточным лимитом | да (заводит карточку) |
| Тренировка | всё выученное вне расписания, можно «последние N» | **нет** |

Тренировка не пишет в FSRS принципиально: алгоритм строит интервалы на допущении,
что повтор случился в назначенный срок. Лишние повторы не вовремя портят оценки
сложности, и расписание начинает врать.

## 10. API для Mini App (этап 5)

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/v1/stats/` | счётчики для главной |
| GET | `/api/v1/queue/due/` | карточки по расписанию |
| GET | `/api/v1/queue/new/` | единицы без прогресса |
| GET | `/api/v1/queue/training/?recent=` | всё выученное, только чтение |
| POST | `/api/v1/review/` | `{entry_id, direction, rating}` → новый `due` |

Классы `APIView` с сериализаторами; `ModelViewSet` не подходит — это не CRUD над
моделью, а вычисляемые очереди.

**Авторизация.** Mini App присылает подписанные `initData`. Проверка в собственном
классе аутентификации DRF: `HMAC_SHA256(key=HMAC_SHA256("WebAppData", bot_token),
msg=data_check_string)` плюс свежесть `auth_date`. Ни один эндпоинт не принимает
`telegram_id` от клиента — только из проверенной подписи. Отсутствующий ученик
заводится при первом валидном запросе.

## 11. Конфигурация

`.env` в корне, читается через `load_dotenv` в `settings.py`. Уже заданные переменные
окружения не перезаписываются, поэтому в Docker побеждает реальное окружение.
`.env.example` содержит только имена.

```
POSTGRES_USER  POSTGRES_PASSWORD  POSTGRES_NAME  POSTGRES_HOST  POSTGRES_PORT
DJANGO_SECRET_KEY  DJANGO_DEBUG
BOT_TOKEN  ADMIN_TELEGRAM_ID  WEBAPP_URL
ANTHROPIC_API_KEY  AI_MODEL
```

Те же `POSTGRES_*` читает `docker-compose.yml`, поэтому данные БД нигде не
дублируются. Внутри контейнера имя базы приходит как `POSTGRES_DB` — это имя образа,
а `POSTGRES_NAME` наше, снаружи.

**Токен бота стоит перевыпустить** через `/revoke` у @BotFather: при отладке он попал
в вывод терминала.

## 12. Открытый вопрос

**Писать ли историю повторов (`ReviewLog`)?**

Таблица «кто, что, когда и как оценил». Нужна для одного: позже подогнать параметры
FSRS под группу — алгоритм умеет учиться на истории и давать интервалы точнее
стандартных.

Это единственное отложенное решение, которое **необратимо**: колонку добавить задним
числом легко, а историю задним числом не восстановить. Цена — строка на каждый ответ,
для десяти человек несколько тысяч строк в месяц.

Ответа от владельца пока нет.

## 13. Принятые решения и обоснования

### Django вместо FastAPI

Владелец поддерживает Django сам. Менять пришлось весь слой данных, иначе в проекте
оказались бы две ORM. Побочный выигрыш: админка закрывает ввод и правку без кода.

Цена: процесс бота асинхронный, а `transaction.atomic()` синхронный. Пока не мешает —
записи одиночные; при пакетных операциях функция пишется синхронной и вызывается
через `asgiref.sync.sync_to_async`.

### Одна таблица `Entry` на слова и фразы

Слово и фраза структурно совпадают. Альтернатива — отдельные таблицы и `UserProgress`
с несколькими nullable FK; сложность переехала бы в слой очередей, самый нагруженный
код проекта.

### Нормализация арабского удалена

`normalize_arabic` приводил слово к скелету без огласовок и ловил дубли, пришедшие с
разной расстановкой харакат. Смысл был при распознавании с фото. Ввод ручной, поэтому
от повторов достаточно ограничения в БД на точную пару. Код восстанавливается из
коммита `171860f`, если на этапе 7 генерации понадобится понимать, какие слова
использованы в предложении.

### Полей меньше, чем в ранних ревизиях

`source` убран — до появления контента от ИИ у всех записей было бы одно значение.
`topic` убран — деления на темы у группы нет, колода плоская. Схема заводится тем
этапом, который ей пользуется, чтобы не замораживать в миграции непроверенное.

### Тестов на `settings` нет

Конфигурация проверяется тем, что проект поднимается. Тесты идут туда, где логика:
разбор строки ввода, права, модели, планировщик.

### Асинхронные тесты требуют `django_db(transaction=True)`

Асинхронные запросы ORM идут по своему соединению и не попадают в транзакцию, которую
откатывает обычный `django_db`. Без маркера записи текут между тестами, и проверки
вида «ничего не сохранилось» ложно проходят.

Остаётся предупреждение в конце прогона: тестовая база не удаляется, потому что
асинхронное соединение остаётся открытым. Попытка закрывать его автоиспользуемой
фикстурой ломает синхронные тесты. Косметика.

## 14. Вне объёма

- Развёртывание: контейнеры `web` и `bot`, VPS, статика — отдельным заходом.
- Распознавание страниц учебника, автоподбор картинок, библиотека простановки
  огласовок — отменены.
- Озвучка, корень и порода глагола — исключены владельцем.
- Статистика по группе, напоминания «пора повторять» — не запрашивались.
- Сущность «Урок», деление на темы, несколько колод, больше одной картинки.
- Режим-тренажёр спряжений: владелец просил формы видеть, а не отрабатывать.
